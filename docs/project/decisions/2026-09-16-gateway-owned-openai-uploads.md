# 2026-09-16 — Gateway-owned OpenAI multipart Uploads

ID: ADR-026 · Status: accepted · Source: user-approved Phase 8 scope with delegated technical contract

**Context.** The gateway-owned Files and Responses Batches contracts currently require one multipart request to create a Batch input File. OpenAI Uploads provide an official multipart lifecycle, but forwarding Parts under a shared provider credential would couple public ownership and retention to the provider and bypass the gateway's storage bounds.

**Decision.** Implement `POST /api/openai/v1/uploads`, `POST /api/openai/v1/uploads/{upload_id}/parts`, `POST /api/openai/v1/uploads/{upload_id}/complete`, and `POST /api/openai/v1/uploads/{upload_id}/cancel` as gateway-owned resources under `files:manage`. The bounded contract accepts only `purpose: "batch"`, a `.jsonl` filename, `mime_type: "application/jsonl"`, and a declared total from 1 through 16 MiB. A pending Upload expires after one hour and accepts at most 16 non-empty encrypted Parts. Completion concatenates 1–16 unique same-Upload Parts in the caller-supplied order and succeeds only when their plaintext byte count exactly matches the declaration. It creates a ready Batch File whose optional `expires_after` is anchored at File creation and ranges from one hour through 30 days. Checksum validation is unsupported; non-empty `md5` is rejected.

**Consequences.** Uploads, Parts, and completed Files belong to the creating inference key and never leave the gateway. Missing and foreign-key Upload IDs return not found; lifecycle operations on expired, completed, or cancelled Uploads return invalid request. Pending Uploads consume bounded retained-resource capacity and their encrypted Parts are removed on cancellation, completion, or expiry. These endpoints perform no provider dispatch, routing, token accounting, or Batch pricing. OpenAI's upstream 8 GB Upload and 64 MB Part limits, other purposes, checksums, provider-owned Uploads, and Vector Stores remain separate contracts.
